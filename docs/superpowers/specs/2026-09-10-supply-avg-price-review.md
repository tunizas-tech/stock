## 0. 한 줄 결론

**핵심 지표 "수급평단"은 우리 앱이 이미 가진 데이터(`data/flow/*.json`)로 오늘 바로 계산된다. pivo-clone 코드는 가져오지 않고, 설계서의 수식과 유효성 규칙만 가져와 우리 방식(순수 함수 + TDD + 관측소/포트폴리오 화면)으로 다시 만든다.** 국민연금·상관계수 화면은 데이터원이 없거나 이미 우리가 더 깊게 한 것이라 보류.

실측(2026-09-08 기준, HD한국조선해양 최근 20거래일):

| 주체 | ΣV | ΣQ | 수급평단 | 종가 | 평단 대비 |
|---|---|---|---|---|---|
| 외국인 | +509.1억 | +127,674주 | **398,719원** | 346,500원 | −13.1% (외국인이 물려 있음) |
| 기관 | −779.8억 | −203,351주 | 383,475원 (**매도평단**) | 346,500원 | 판 가격보다 9.6% 싸짐 |

이 표가 곧 이 기능이 보여줄 것이다. 계산에 새 API·새 라이브러리·새 DB가 하나도 필요 없었다.

## 1. pivo-clone이 뭔가 (분석 요약)

### 1.1 핵심 아이디어 — 수급평단

> "외국인이 최근 W일 동안 산 주식의 **평균 단가**는 얼마인가? 지금 주가는 그보다 위인가 아래인가?"

```
avg_price(종목, 주체, W) = Σ 순매수금액 / Σ 순매수수량      (최근 W거래일, W ∈ {1, 5, 20, 60})
return_pct              = (현재가 − avg_price) / avg_price × 100
```

**왜 의미가 있나:** 관측소 ②가 보여주는 "20일 순매수 −655억"은 *얼마나* 샀는지만 말한다. 수급평단은 *얼마에* 샀는지를 말한다. 외국인이 40만원에 사 모았는데 지금 34만원이면 "외국인이 −13% 물려 있다"는 한 줄이 된다. 방향을 예측하는 지표가 아니라, **그 주체가 지금 이익인지 손실인지**를 기술하는 지표다. 관측소의 정직성 원칙("이 숫자는 다음 수익률을 예측하지 못한다")과 충돌하지 않는다.

**유효성 규칙 (설계서에서 그대로 가져올 것):**

| 조건 | 결과 | 이유 |
|---|---|---|
| ΣQ = 0 | null | 0으로 나눌 수 없음 |
| sign(ΣV) ≠ sign(ΣQ) | null | 비싸게 사고 싸게 팔아 금액·수량 부호가 엇갈린 창 — 평단이 무의미 |
| ΣQ < 0 이고 ΣV < 0 | 유효, **side = 'sell'** | 매도평단. "물렸다/이익이다" 해석이 뒤집히므로 UI에 반드시 표시 |
| 창 안에 액면분할·감자 등 | null + 배지 | 수량 단위가 달라져 합산 불가 |
| \|ΣQ\| < 평균거래량 × 0.001 | 제외 | 노이즈 |

### 1.2 부가 기능 4개

| 화면 | 내용 | 우리 앱 관점 |
|---|---|---|
| `/flow` 레이더 | 종목 리스트 + 상세(3주체 평단 카드, 현재가 위치 바, 가격+평단선+순매수막대 차트) | **채택** — 핵심 |
| `/flow/new-hot` | 전환 감지: 직전 5일 합 vs 최근 3일 합의 부호가 바뀌고 \|최근\| ≥ 10억 | 채택 후보 — 우리 `flowPersistence`(streak)와 겹침, 2단계에서 판단 |
| `/flow/nps` | 국민연금 지분 변동 (DART·SEC EDGAR) | **보류** — 클론에도 코드 0줄, 데이터원 없음 |
| `/flow/correlation` | 미국↔한국 로그수익률 Pearson, lag=1, 창 20/50/100 | **보류** — 우리는 이미 `us-kr-transfer` 설계에서 갭 상관 0.712까지 확인하고 "매매로 못 먹는다"로 결론 냄 |

### 1.3 클론 코드의 상태 — 왜 코드를 가져오지 않는가

- **실행 불가**: frontend에 package.json·tsconfig·root layout 없음. backend는 `ingest_flow`·`build_flow_agg`만 있고 `sync_master`·`ingest_price`가 없어 집계가 0행이 된다. 마이그레이션 없음.
- **스택 불일치**: FastAPI/SQLAlchemy/pykrx(Python) — 우리는 Next.js/TypeScript 단일 스택. pykrx는 KRX 로그인 필요, 2,700종목 × 2 = 하루 5,400 요청.
- **설계 결함**: `market_cap`이 채워지지 않아 기본 필터인 `strong_accum`이 영원히 빈 결과; `has_corp_action`은 항상 false; `avg_price_series` 테이블은 하루 420만 행 증가; NEW&HOT 코드가 설계서와 다른 창(`flows[-8:-3]`)을 쓰고 길이 가드 버그; 기관⊃연기금 이중 집계를 UI가 안 알림.
- **건질 것**: 설계서(`docs/01-design.md` = `수급평단-설계서.md`)의 수식·유효성 규칙·화면 구성, 그리고 `flow_calc` 테스트 19개의 케이스 목록(우리 테스트 설계에 참고).

> 배울 개념: **"설계는 가져오고 코드는 안 가져온다"**는 판단 기준. 코드 이식 비용(스택 변환 + 버그 상속) > 재작성 비용(우리 데이터 구조에 맞춰 순수 함수 50줄)일 때 재작성이 싸다. TDD가 있으면 재작성이 더 안전하기까지 하다.

## 2. 우리 앱에 구현 가능한가 — 항목별 판정

| 항목 | 필요한 것 | 우리 앱에 있나 | 판정 |
|---|---|---|---|
| 일별 주체별 순매수 **금액** | 외국인·기관·개인 | `FlowDay.foreign/institution/individual` (백만원) | ✅ |
| 일별 주체별 순매수 **수량** | 같음 | `FlowDay.foreignQty/institutionQty/individualQty` (주) — 백필 1,230일 전부 채워짐 확인 | ✅ |
| 일별 종가 | 수익률 계산용 | `FlowDay.close` | ✅ |
| 종목 범위 | 2,700종목 | **30종목**(`FLOW_UNIVERSE`) + 보유종목 중 유니버스 밖 9종목은 없음 | ⚠️ 유니버스 한정 |
| 연기금(pension) 분리 | pivo 3주체 = 외국인·기관·**연기금** | KIS `inquire-investor`는 외국인·기관·개인만 | ❌ → 3주체를 **외국인·기관·개인**으로 정의 |
| 시가총액 (strong 분류용) | `net_ratio = ΣV / market_cap` | `Fundamentals.marketCap`(KIS 시세, 억원) — 시세 요청 시점 값 | ✅ (스냅샷) |
| 액면분할 감지 | 창 무효화 | 없음. 종가 급변(전일 대비 ±40%↑)으로 근사 가능 | ⚠️ 휴리스틱 |
| 차트 | 가격 + 평단선 + 순매수 막대 | `recharts` 이미 사용 중(`CandleChart.tsx`) | ✅ |
| 국민연금 | DART/EDGAR | 없음 | ❌ 보류 |
| 상관계수 | 미국 섹터 ETF 캔들 | 지수·XLK·XLV·SOXX만 | 이미 다른 설계에서 결론 → 보류 |

**결론: 핵심(수급평단 + 레이더 화면)은 데이터·라이브러리 추가 없이 가능.** 제약은 "30종목 유니버스"뿐이고, 이건 관측소 ②가 이미 안고 있는 같은 제약이다(유니버스 밖 산업은 "관측 유니버스 밖 — 수급 없음"으로 이미 표시 중).

### 우리 데이터의 함정 (구현 시 반드시 반영)

1. **단위**: `foreign`은 백만원, `foreignQty`는 주 → `avg = ΣV × 1,000,000 / ΣQ` (원). 단위 실수 하나로 평단이 100만 배 틀린다. 테스트 첫 케이스가 이것이어야 한다.
2. **백필 구간의 개인 = 0**: 네이버 백필(2021~2026-08)은 외국인·기관만 있고 개인은 0. 개인 평단은 KIS 적재가 시작된 날(2026-08 말) 이후 창에서만 유효 → `individual`은 ΣQ=0 규칙에 자연히 걸리지만, "데이터 없음"과 "매매 없음"을 UI에서 구분해야 한다.
3. **KIS 30일 창**: 60일 평단은 백필이 있어 가능하지만, 유니버스에 새로 추가한 종목은 백필 전까지 60일이 안 찬다 → `tradingDays < W`면 `(N일치)` 표기(비교 카드에서 이미 쓰는 방식).
4. **기관 ⊃ 연기금**: KIS 기관계는 연기금·투신·보험 등을 합친 값. 설명 문구에 한 줄 명시.

## 3. 설계 — 우리 앱 안에서 어디에, 어떻게

### 3.1 계산층 `src/lib/flow/avg-price.ts` (순수 함수, TDD)

```ts
export type FlowActor = "foreign" | "institution" | "individual";
export type AvgWindow = 1 | 5 | 20 | 60;

export interface SupplyAvgPrice {
  actor: FlowActor;
  window: AvgWindow;
  avgPrice: number | null;        // 원. null이면 reason에 이유
  side: "buy" | "sell" | null;    // ΣQ>0 → buy, ΣQ<0 → sell
  returnPct: number | null;       // (close − avg) / avg × 100
  sumValue: number;               // 백만원
  sumQty: number;                 // 주
  tradingDays: number;            // 실제 창에 들어간 일수
  reason?: "zero-qty" | "sign-mismatch" | "corp-action" | "noise" | "short-window";
}

export function supplyAvgPrice(days: FlowDay[], actor: FlowActor, window: AvgWindow): SupplyAvgPrice;
export function supplyAvgSeries(days: FlowDay[], actor: FlowActor, window: AvgWindow): { date: string; avgPrice: number | null }[];
// 롤링: 각 날짜 t에 대해 [t−W+1, t] 창의 평단 — 차트의 "평단선"
```

- 입력은 이미 있는 `FlowDay`. 새 타입·새 적재 없음.
- `aggregate.ts`에 넣지 않고 새 파일 — `aggregate.ts`는 섹터 합산, 이 파일은 종목 단가. 역할이 다르다.
- 테스트 케이스(설계서 19개 중 우리 데이터에 맞는 것 + 함정 1~3):
  단위 환산 / ΣQ=0 → null / 부호 불일치 → null / 매도평단 side=sell / returnPct 부호 / window 슬라이싱 / 짧은 창 tradingDays / 노이즈 제외 / 롤링 시리즈 길이·앞쪽 null / 종가 ±40% 급변 → corp-action.

### 3.2 API — `/api/observatory`에 얹지 않고 종목 단위 라우트

- `GET /api/flow/[ticker]?window=20` → `{ ticker, name, sector, close, actors: SupplyAvgPrice[3], series: {...} }`
- 이유: 관측소 응답은 이미 크고(12섹터×3창), 평단은 종목을 골라야 나오는 상세 데이터. `force-dynamic`, `data/flow/<ticker>.json` 하나만 읽는다.

### 3.3 화면 — 2곳, 작게

**(a) `/portfolio` 보유종목 행 확장** — 유니버스 안 종목에 한해 한 줄:
`외국인 평단 398,719 (−13.1%) · 기관 매도평단 383,475` — 내 평단 옆에 놓이면 "나는 외국인보다 싸게 샀나"가 바로 읽힌다. 이 앱의 존재 이유(내 보유와 시장을 잇기)에 가장 가깝다.

**(b) 관측소 ③ "수급평단 레이더"** — 설계서의 레이더 화면을 축소해 이식:
- 왼쪽: 유니버스 30종목 리스트, 열 = 외국인 20일 평단 대비 %, 기관 %, 분류(accum/distrib), 정렬 가능
- 오른쪽(선택 시): 3주체 카드 + 현재가 위치 바 + Recharts `ComposedChart`(종가 선 + 평단 롤링선 + 순매수 막대)
- 창 토글 5/20/60. 정직성 캡션 유지: "평단은 그 주체의 손익 상태를 기술할 뿐, 다음 수익률을 예측하지 않는다."

### 3.4 분류(category)는 단순화

설계서의 `strong_accum`(net_ratio ≥ 0.5% & buy_days ≥ 60%)은 시가총액이 필요해 클론에서 실패한 지점. 우리는 1단계에서 **분류를 만들지 않는다.** 이미 있는 `flowPersistence`(연속일·매수일 비율)가 같은 정보를 더 정직하게 준다. 시가총액 비율은 2단계에서 `Fundamentals.marketCap` 스냅샷으로 검토.

## 4. 단계별 계획

| 단계 | 내용 | 산출물 | 사용자가 배우는 개념 |
|---|---|---|---|
| **1** | `supplyAvgPrice` 순수 함수 + 테스트 → `/api/flow/[ticker]` → `/portfolio` 보유행에 외국인·기관 평단 한 줄 | 로컬에서 내 평단 vs 외국인 평단 확인 | 가중평균(ΣV/ΣQ)이 산술평균과 다른 이유, 단위 환산 테스트 |
| **2** | `supplyAvgSeries` 롤링 + 관측소 ③ 레이더(리스트 + 상세 차트) | 30종목 레이더 | 롤링 윈도우(슬라이딩 창)와 O(n·W) vs 누적합 O(n) |
| **3** | 전환 감지(NEW&HOT) — `flowPersistence`와 합쳐 "최근 3일이 직전 5일과 부호가 바뀐 종목" 목록. 설계서 버그(겹치는 창) 고쳐서 | 관측소 ③ 상단 배지 | 겹치는 창 vs 겹치지 않는 창의 차이 |
| 4 (보류) | 시가총액 대비 강도 분류, 액면분할 정식 처리(KIS 기업정보), 유니버스 확장 | — | — |
| 보류 | 국민연금, 상관계수 화면 | — | 데이터원 없음 / 이미 결론남 |

각 단계는 브랜치 하나(`feat/supply-avg-price-1` …), TDD(RED 확인 → GREEN), 로컬 :3000 확인 → 사용자 "됐어" → main merge → push 자동배포. DB 스키마 변경 없음(전부 `data/flow` 파일 계산).

**1단계 예상 규모**: 계산 ~80줄 + 테스트 ~120줄 + API ~40줄 + UI ~60줄. 관측소 ② 만들 때와 비슷한 크기.

**1단계를 다음 작업으로 진행할 것을 권한다.** 근거: (1) 데이터가 이미 있어 적재·스키마 작업이 0, (2) 이 앱의 핵심 화면인 `/portfolio`에 "내 평단 vs 큰손 평단"이라는 직관적인 한 줄이 생긴다, (3) 방금 만든 비교 카드가 "산업 단위" 수급이면 이건 "종목 단위" 수급으로 자연스럽게 한 층 내려간다.

승인 전에는 구현하지 않는다. 승인 시 `superpowers:writing-plans`로 1단계 실행 계획(파일·테스트·순서)을 따로 쓴다.

`clone/`은 참고용으로 두되(tsconfig exclude·.gitignore 처리 완료) 설계서 한 파일(`수급평단-설계서.md`)만 남기고 나머지는 지워도 무방하다 — 코드는 가져오지 않기로 했으므로.
